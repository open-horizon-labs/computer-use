# Lightweight off-screen browsing

For a small browser-only task without user logins, use an available isolated browser capability that can stay off the physical screen. No full desktop guest is needed just to read pages or fill a simple form. Confirm the provider's isolation and observation/input support; do not assume headless or hidden means correctly isolated.

The optional OH adapter supports an owned Chromium profile on a required verified virtual display. It is useful when installed and available; it is not a measured speed winner and has not been qualified for locked-host use. Enable it only for the task through [setup](setup.md). It never substitutes the user's profile or physical screen. This path uses the virtual monitor, not Mission Control; the retained Space-moving helper is not configured as a fallback.

Start with do(capability="off_screen", goal="Open isolated browser", steps=[{do:"open_tab", url:"https://example.com", expect:null}]). Reuse its context_id; call look before choosing visible controls, then do with independent outcomes. Reuse look_id for where.lines predicates; filters need observed evidence. A null final expect is delivered_unverified, not success. One off-screen context is active per server.

The optional OH display owner records pending ownership in CUA_CACHE_DIR/display-fault.json (default ~/.cache/computer-use/display-fault.json). Another creator or a restarted controller refuses while that record exists. Startup and teardown uncertainty retain the owner and latch further creation; there is no automatic kill, retry, or fault reset. Healthy shutdown clears ownership only after an independent display query confirms removal. Operator recovery requires inspecting the recorded controller/owner, confirming the host and physical displays are stable and no owned virtual display remains, then archiving/removing the record. Do not remove it while an owner or controller is still running; PID values are diagnostic evidence and must be revalidated before any process action. Process exit can itself release displays, and these safeguards do not cancel macOS calls or establish locked-host reliability.

Browser launch focus evidence appears in the existing trace as agent_browser_focus. Frontmost-app restoration is independently observed; keyboard/text input routes remain unknown. The report covers launch only, not continuous focus isolation.

For explicitly selected hybrid research, CUA_DISPLAY_BACKEND=spaceo uses a prebuilt CUA_SPACEO_DISPLAY_WORKER linked to the reviewed SpaceOKit checkout. OH retains its browser, Driver and observation binding; the worker owns only a Stage. Build it explicitly with scripts/build_spaceo_display_worker.py, never during a runtime call. This backend is not live-qualified. It shares the OH exclusion record, honors SpaceO's native circuit, refuses other known display owners, and checks a separate online inventory and original topology before clearing ownership. It never starts SpaceO's daemon, resets a fault or substitutes a physical display. The default remains space-mover.

If a browser/display prerequisite fails, repair supported setup or use a task-owned Spaces guest when that satisfies the request. Do not keep retrying a broken display or silently route to the host screen. For logins in the user's browser, use OBO instead. Provider commands/secrets remain external; no specialist models or archived native/VNC/terminal routes are needed.
